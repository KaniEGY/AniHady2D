# Stick cross-network relay architecture

Status: **design / implementation branch only — not deployed and not part of the stable release**  
Date: 2026-11-18

## Goal

Let two Stick users on different networks join the same Drawing or Animation room without requiring Tailscale, ZeroTier, manual port forwarding, or a public IPv4 address.

The existing transports remain supported as fallbacks:

- LAN discovery
- direct IP / DNS TCP connection
- Tailscale / ZeroTier private overlay
- the current 8-digit room code and password flow

A relay must not be described as ready until it has been deployed and tested with two separate Windows PCs on separate Internet connections.

## Recommended phase 1: WSS room relay

Use a Cloudflare Worker as the public HTTPS/WSS entry point and one Durable Object per room as the stateful WebSocket coordinator.

```
Stick host ── WSS/TLS ──┐
                        ├── Worker ── Durable Object(room)
Stick guest ─ WSS/TLS ─┘
```

Why this first:

- WebSockets map cleanly to Stick's current bidirectional collaboration packets.
- No inbound port is required on either user's router.
- Durable Objects are designed for stateful multi-client coordination.
- The Hibernation WebSocket API can keep idle sockets connected without charging normal duration while the object is eligible to hibernate.
- This is simpler to validate than introducing WebRTC signalling, ICE and TURN in the same change.

Official references:
- https://developers.cloudflare.com/durable-objects/best-practices/websockets/
- https://developers.cloudflare.com/durable-objects/platform/pricing/

## Security model

1. Only `wss://` is accepted by release builds. Plain `ws://` is allowed only for explicit localhost development.
2. A room uses a cryptographically random opaque room ID. The visible 8-digit Stick code remains a human-friendly label and is **not** an authentication secret.
3. Joining requires a short-lived random invitation ticket. Tickets are generated by the service, expire, and can be revoked when the host closes the room.
4. Cloudflare account tokens, API tokens and server signing keys are stored only as deployment secrets. They are never compiled into `Stick.exe`, committed to GitHub, or placed in an invite link.
5. Room passwords are not stored in invitation URLs.
6. Relay traffic is transient. Phase 1 does not persist project files, audio, drawings or chat payloads after the room closes.
7. Enforce room capacity, per-client message size, packet-rate limits and connection-rate limits before forwarding.
8. Reject protocol-version mismatches before accepting collaboration traffic.
9. Existing application packet validation and maximum packet limits stay in force.
10. Before a public rollout, add application-level end-to-end encryption for collaboration payloads if the threat model requires the relay provider itself to be unable to inspect content. WSS/TLS protects traffic in transit but is not the same as E2E encryption.

## Proposed public API

All endpoint names are provisional until implementation tests pass.

- `POST /v1/rooms` — host creates a room and receives a room ID, host ticket and guest invite.
- `POST /v1/rooms/{room}/invite` — host rotates/creates a short-lived guest ticket.
- `GET /v1/rooms/{room}/ws?ticket=...` — upgrade to WebSocket.
- `DELETE /v1/rooms/{room}` — host closes the room and invalidates tickets.

The Stick invite can later evolve to something like:

```
stick://join?relay=relay.example.com&room=<opaque-id>&ticket=<short-lived-ticket>&mode=drawing
```

The current direct invitation remains valid and is not removed.

## Message transport

The relay forwards the existing collaboration protocol as binary WebSocket messages instead of redesigning project operations.

Before forwarding:

- cap each incoming WebSocket message below both Stick's existing packet limit and the provider platform limit;
- validate room membership and protocol version;
- coalesce high-frequency cursor packets;
- apply bounded queues so one slow client cannot exhaust memory;
- disconnect abusive or permanently lagging clients;
- never deserialize untrusted collaboration payloads on the relay unless strictly required for routing.

## Failure / fallback behavior

The client must clearly distinguish:

- relay service unavailable;
- invalid/expired invite;
- room full;
- incompatible Stick version;
- temporary reconnect;
- local Internet failure.

Failure of the relay must not disable LAN, Direct IP/DNS, Tailscale or ZeroTier joins.

## Cost and service requirements

Required for production deployment:

- a Cloudflare account;
- a Worker + SQLite-backed Durable Object namespace;
- a public `https://` / `wss://` endpoint (a custom domain is optional);
- server-only secrets configured in Cloudflare, never in GitHub source.

As of 2026-11-18 Cloudflare documents Durable Objects on Free and Paid Workers plans. Current documented free limits include 100,000 requests/day and 13,000 GB-s/day for Durable Objects; paid usage has separate included quotas and metered overage. Re-check official pricing immediately before production deployment.

## Phase 2 option: WebRTC + STUN/TURN

If relay bandwidth becomes the dominant cost, evaluate WebRTC after phase 1 is stable:

1. Use the WSS Durable Object only for signalling.
2. Try direct WebRTC connectivity using STUN.
3. Fall back to managed TURN only when NAT/firewall conditions prevent P2P.

Cloudflare currently documents `stun.cloudflare.com` as free/unlimited and Realtime TURN at $0.05 per outbound real-time GB with a 1,000 GB free tier. These terms can change and must be verified before enabling billing.

Official references:
- https://developers.cloudflare.com/realtime/turn/
- https://developers.cloudflare.com/realtime/turn/faq/

## Implementation milestones

### R1 — transport abstraction
- Separate collaboration session logic from raw `TcpStream`.
- Keep TCP behavior byte-for-byte compatible.
- Add unit tests that feed identical packet sequences through a mock transport.

### R2 — relay client
- Add a WSS client transport with strict TLS verification.
- Add relay join/create UI without removing old methods.
- Parse relay invite fields separately from direct-address invites.
- No credentials embedded in the executable.

### R3 — relay service
- Durable Object room lifecycle.
- short-lived host/guest tickets.
- capacity/rate/message limits.
- reconnect and host-close behavior.
- logs contain room/session metadata only, not collaboration payload contents.

### R4 — real network QA
Required before changing the UI label to “ready”:
- two separate Windows PCs;
- two different Internet connections / NATs;
- create room, join, draw concurrently, animate, cursor sync, resync, disconnect/reconnect;
- wrong/expired invite rejection;
- room-full and version-mismatch rejection;
- long idle connection then resume;
- packet burst / slow-client test;
- verify LAN/direct/private-overlay fallback still works.

### R5 — staged rollout
- experimental opt-in first;
- telemetry limited to service health and anonymous error classes;
- spending limit configured;
- rollback switch that disables relay discovery without affecting local transports.

## Explicit non-claims

This branch does **not** mean:
- a relay service has been deployed;
- Cloudflare credentials exist;
- NAT traversal has been tested;
- two remote PCs have connected successfully;
- the feature is production ready.

Those statements become true only after the deployment and R4 acceptance tests are completed.
